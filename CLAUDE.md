# Hitchcock migration map

Interactive map of every documented migration among the direct ancestors of
Margaret Jean Hitchcock. Margaret is a synthetic root person (b. 2026,
Alexandria VA), the daughter of James Albert Hitchcock (repo owner) and
Jennie Anne Askew. Rooting at her unifies both family trees: 1,280 people
and 897 routes spanning 1545–2026, from England, Ireland, Scotland, Germany,
Switzerland and Sweden through colonial New England and Virginia to the
South and Midwest.

- Live: https://jhitchcock64.github.io/-hitchcock-migration-map/
- Hosting: GitHub Pages, serving the root of `main` (`index.html`, `data.js`,
  `basemap/`). Pushing to `main` deploys, usually within a minute or two.
- Source of truth for the family data: James's Ancestry tree, exported as a
  GEDCOM. The GEDCOM is NOT in the repo and must never be committed (it
  contains living people; `.gitignore` blocks `*.ged` and `*.zip`).

## Data pipeline (summary; details in pipeline/RUNBOOK.md)

```
GEDCOM="/path/to/export.ged" bash pipeline/project/run_pipeline.sh   # rebuild arrays (Git Bash)
python pipeline/project/diff_shipped.py data.js                      # compare with the live data
python pipeline/project/write_data_js.py data.js                     # write the arrays into data.js
python tools/check_page.py index.html                                # smoke test
```

Pure Python 3 standard library. It runs from any folder, detects the
per-export James+Jennie family ID automatically, and pins `PYTHONHASHSEED=0`
(and `PYTHONUTF8=1`, for Windows) for reproducible output. Verified
2026-09-24 on James's Windows laptop with the 2026-09-23 export: output is
byte-identical to the live data on all six arrays.

Stages:
1. `01_extract_ancestors.py` parses the GEDCOM, injects synthetic Margaret,
   and walks her ancestors → `indi.json`, `fam.json`, `ancestors.json`.
2. `02_extract_events.py` pulls birth/residence/death events and applies
   hand corrections → `events.json`.
3. `geocoder.py` (imported, not run) turns raw place strings into
   `(label, lat, lon, tier)`.
4. `03_build_legs.py` builds each person's stops and legs → `legs.json`.
5. `04_build_routes.py` builds route geometry, including ocean paths →
   `migration_routes.geojson`.
6. `build2/build_anchors.py` and `build_family_tags.py` link routes to people
   and mark families traveling together.
7. `build2/rebuild_all_data.py` produces the six arrays the page uses:
   `routes_prepared.json` → ROUTES, `clusters_prepared.json` → CLUSTERS,
   `places_prepared.json` → PLACES, `search_index.json` → SEARCH_INDEX,
   `person_graph.json` → GRAPH, `person_legs.json` → PERSON_LEGS.
8. `write_data_js.py` writes them into `data.js` (it replaced `graft.py`
   when the data moved out of `index.html`), keeping BASEMAP, REF_CITIES and
   VB byte for byte.

Ocean crossings are computed in the pipeline and shipped as finished
coordinate paths, so any renderer can draw them as-is.

The detailed basemap has its own build, independent of the GEDCOM:
`python pipeline/basemap/build_basemap.py` (about 2 minutes). It reads public-
domain data from `pipeline/basemap/cache/` (git-ignored; the script's
docstring lists the download URLs): US Census county boundaries 1:500k and
the gazetteer of places, and Natural Earth 1:10m countries, lakes, rivers
and first-level divisions. Rebuilding with the same inputs reproduces
`basemap/` exactly. County lines are modern Census boundaries, not
historical ones.

## Coordinates

Everything in the page is in projected units: `x = lon + 35` (wrapped to
[-180,180)), `y = 65 - lat`. This is plain equirectangular, centered on the
Atlantic. The default view spans `VB = {x0:-70, y0:0, w:123, h:58}`.

## Rendering (index.html, rebuilt 2026-09 for speed)

On James's laptop the old page dropped 42–91% of frames while zooming and
panning; the rebuild drops 0–1%. Why the old one was slow, measured: Canvas 2D
takes 100–300 ms to stroke ~900 wide translucent routes on an integrated GPU,
and the GPU re-rasterised the SVG basemap every frame. JavaScript was never
the bottleneck (4–10 ms per frame).

Layers, bottom to top (all in `#map-wrap`, which clips them):
- `#routes-gl` (WebGL2, viewport-sized): the basemap and all routes, cluster
  bands and arrowheads, redrawn every frame at the current view.
  - Basemap (`drawBasemapGL`): below zoom 3.5 the original `BASEMAP` data
    (so the default view looks as it always did); from 3.5 detail tiles from
    `basemap/` in three bands (3.5×, 10×, 30×), loaded on demand. Fills use
    the stencil buffer (SVG's nonzero rule); lines are instanced quads with
    the old SVG styles in map units, capped in screen px above ~10× so lines
    don't swell into bands. County-level lines from 5×.
  - Routes (`drawRoutesGL`): one instanced "capsule" per segment reproduces
    Canvas 2D exactly: round joins/caps, per-stroke alpha with no
    self-overlap darkening (per-stroke depth + MSAA), twin strokes, dashes
    with round caps, arrowheads, same draw order. Instances are rebuilt only
    when the target, focus or aggregation state changes.
- `#thread-canvas` (Canvas 2D, viewport-sized): the focused thread / path /
  era / surname segments (`drawThread`), a few dozen strokes.
- `#map-stage` (overscanned by ~30% on each side): `#overlay-svg` with place
  dots, reference-city dots and the target's ring. During a gesture the
  stage is only moved by a CSS transform and redrawn when the gesture
  settles (`gestureFrame` / `settle`); it also holds `#routes-canvas`, used
  only by the Canvas 2D fallback.
- Labels: pooled HTML divs (place labels, reference cities, towns from 7×,
  the target's label), positioned by transform and snapped to device pixels;
  laid out (`updateLabels`) when a gesture settles.
- `#zoom-capture`: receives mouse and touch input. Zoom is custom
  (`applyZoomAt`, range 1–60×).

Frame flow: input → `scheduleRedraw()` → one `gestureFrame()` per animation
frame (WebGL redraw + CSS transforms); a wheel zoom settles 150 ms after its
last event, a drag or pinch when released → `settle()` → `renderNow()` +
`updateLabels()`. `redrawAll()` only schedules a `renderNow()` for the next
frame, so several requests in one frame cost one render. Hover hit-tests
against screen polylines computed on demand (`ensureScreenCache`).

Fallbacks: without WebGL2 (or after a lost GPU context), routes draw with
Canvas 2D on the stage and the basemap is drawn off the main thread by a
worker into a bitmap (the pre-WebGL v2 design). Keep them working.

Routes are drawn with:
- Color: `colorForYear(mean_year)`, a rank-based 7-stop palette (see below).
- Width: `lwFor(count)`, by number of ancestors on the route.
- Twin stroke for `family_group` (confirmed family traveling together).
- Dashed for `oscillation` (repeated back-and-forth between nearby towns).
- Arrowheads at the destination.
- Below zoom 4.5 (`AGGREGATE_ZOOM_THRESHOLD`), routes that belong to a
  cluster with at least 2 visible members are hidden and the cluster band is
  drawn instead.

Relevance: `setTarget(person)` computes `TARGET_ANCESTOR_SET`. A route is
drawn if any of its `anchor_ids` is in that set. `recomputeClusterVisibility()`
runs once per target change.

Modes (`#search-modes` buttons, `searchMode`):
- **Family journey** (default): choose a target person; shows the routes of
  that person's ancestors converging on them. The default target is Margaret.
- **Life journey**: one person's own legs from `PERSON_LEGS`.
- **Path between**: the genealogical path between two people (`findPath` /
  `assemblePath`), with status text in `#path-status`.
- **Time period**: from/to year inputs, a play button that steps a window
  2 years every 200 ms across the data's year range, and an optional person
  filter (`#era-person-*`).
- **Surname**: filter routes by surname.

Interaction:
- Hover: `handleHover` → hit-test clusters and routes (`distToSeg`) →
  tooltips. No hover mid-gesture.
- Click: `handleClick` → a route picker if several overlap, otherwise focus
  the route's generational thread to the target (`focusThread`,
  `renderFocusedChain`), with `#focus-panel` and a dropdown; everything else
  dims.
- Zoom buttons `#zoomIn/#zoomOut/#zoomReset`, level shown in `#zoomLevel`;
  wheel, pinch and drag all work.

Color scale (settled 2026-09-24 after several rounds; don't change without
asking James):
- Stops, oldest → newest: `#0f8a7a #2050d6 #8033d6 #e0359e #f0453f #ff8c1a #e8c020`
  (teal → blue → violet → magenta → red → orange → gold).
- Rank/percentile mapping (`rankT`): a year's color reflects its position
  among all route years, not its place in 1545–2026. About half the routes
  fall in 1750–1870; a linear scale squeezed them into one hue.
- The legend gradient (`#cbGradientCanvas`) is painted from the same
  function, running by year left to right. Its labels (earliest / median /
  latest route year) and the header's year range are derived from the data;
  the median label sits where the median year's colour is (61% across), not
  at the centre.
- Rejected, for the record: RdYlBu (its pale-yellow midpoint vanished on
  the tan basemap) and viridis.

Data formats (all coordinates in projected units):
- ROUTES[i]: `id, curve, count, mean_year, min_year, max_year, from, to,
  people[], anchor, anchor_ids[], family_group`, optionally `cluster` and
  `oscillation`. `curve` is either
  `{mode:"bow", x1,y1,cx,cy,x2,y2}` (quadratic arc) or
  `{mode:"path", coords:[[x,y],...]}` (ocean crossings and other waypointed
  routes).
- CLUSTERS[i]: `id, curve, count, mean_year, min_year, max_year, from, to,
  members[]` (indices into ROUTES).
- PLACES[i]: `label, x, y, touches, tier` (1–3; drives label priority).
- SEARCH_INDEX[i]: `id, name, birt, has_moves, has_place`.
- GRAPH: `{james_id (actually Margaret's id), sibling_ids, people:{id:
  {name, surname, by (birth year), bplace, bx, by_y, fx, fy, fplace?, parents[]}}}`.
- PERSON_LEGS: `{id: [{from, to, year, x1,y1,x2,y2, cx,cy, ocean?, waypts?}]}`.
- BASEMAP: SVG path strings, `land_far, land_near, states_far, states_near,
  lakes, rivers, central_america`. Not produced by the pipeline; baked in
  from an earlier session. The WebGL basemap uses the `_far` versions below
  zoom 3.5; the bitmap fallback uses both.
- Also static in `data.js`: REF_CITIES (reference city labels) and VB.
- `basemap/index.js` (BASEMAP_INDEX: bands, tile size, which tiles exist),
  `basemap/detail_<band>_<tx>_<ty>.js` (one tile: layers land, lakes as
  rings; coast, border, seam, state, county, rivers, lakeEdge as lines; each
  shape a flat `[x0, y0, dx, dy, ...]` in units of `quant`), and
  `basemap/towns.js` (BASEMAP_TOWNS: `[name, state, x, y]`, most prominent
  first).

Scale: 897 routes, 61 clusters, 493 places, 1,280 people, 595 of them with
movement (1,277 legs). That's small; if the map feels slow, look at how it's
drawn, not how much it draws.

## Hard-won rules

1. The data arrays in `data.js` are generated. Regenerate with the pipeline
   and `write_data_js.py`. Never hand-edit or string-splice them. (On
   2026-09-23 a splice silently lost to stale duplicate keys and shipped
   broken data.) `basemap/` is generated too: rebuild it, don't edit it.
2. Before shipping data changes, run `diff_shipped.py` against the live
   `data.js`. Everyone who matched before must still match, and every
   difference needs an explanation.
3. Check in a real browser before pushing: `tools/check_page.py`, then look
   at the screenshot. Checking data alone isn't enough. For rendering
   changes also run `tools/parity_check.py` and `tools/compare_views.py`
   against `legacy.html` or the previous commit, and profile on James's
   laptop with `tools/profile_page.py --headed --dpr 1.5`.
4. GEDCOM individual IDs (`@I...@`) are stable across exports. Family IDs
   (`@F...@`) change every export.
5. A GEDCOM person can have several NAME records. A blank one mustn't
   overwrite a real name (this once hid Daniel Baskett from search). Fixed in
   stages 1 and 2.
6. Don't assume. Read the file, run the code, check the output.
7. Performance numbers from one run are noise-prone on his laptop
   (sporadic 33 ms frames at 1× regardless of code). Compare versions with
   alternating repeated runs before concluding anything.

## Recent research that shaped the current data (context only)

In September 2026 James established, from Cumberland and Goochland County
records, that Thomas Baskett (b. ~1739, d. 1773 Cumberland) was the son of
Daniel Baskett and Mary Godbey. The long-assumed "Thomas Baskett Sr.
(b. 1716)" was removed from the tree; `tools/check_page.py` checks that he
stays gone. The Godbey line runs back to Thomas Godbey Sr., who sailed on the
Sea Venture: Plymouth → Bermuda (wrecked 1609) → Jamestown (1610).
